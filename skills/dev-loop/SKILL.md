# 開発の流れ（dev-loop）

コードを変える作業の、着手から commit までの流れ。レーンの回し方は [lanes](../lanes/SKILL.md)、レビューの周回は [review-loop](../review-loop/SKILL.md) に従う。

## 0. プロジェクトのルールが先
- 対象リポジトリに自分たちの開発ルール（`AGENTS.md`・`CLAUDE.md`・`CONTRIBUTING.md`・`docs/` の手順など）があれば、**まずそれを読み、食い違ったらそちらに従う**。このスキルは、ルールが無いところを埋める最低限の決まり。
- テストの道具・コマンド・ブランチの運用・デプロイの手順は、プロジェクトのものを使う。

## 1. PLAN を出して、人の GO を待つ
- 実装に入る前に、次の 5 つを短く書いて人に見せる。**GO が出るまでコードを変えない**。
  - 目的（何を解決するか）／技術方針（どう作るか・なぜその方法か）／範囲（やること・やらないこと）／触るファイル／完了条件（何が確かめられたら終わりか）
- 人が「すぐ直して」と言った小さなバグ修正は、PLAN を省いてよい。
- **レーンの中（人に聞き返せない実行）では GO を待たない**。渡された指示書が GO 済みの PLAN にあたる。指示書に無い判断が要るときは、勝手に決めずに止めて、理由を最終報告に書く。
- 決めるのが人の仕事のもの（仕様の選択・費用のかかる操作・本番への影響）は、選択肢と自分のおすすめを添えて聞く。

## 2. 実装
- 大きい作業（複数のファイル・時間がかかる・並列にできる）は、触るファイルが重ならない小さなレーンに分けて起動する（[lanes](../lanes/SKILL.md)）。
- 小さい作業（数行の修正・文言・設定 1 つ）は、レーンを使わず直接直してよい。そのときも 3〜5 の流れは同じ。
- 頼まれた範囲の外は触らない。範囲の外で見つけた問題は、直さずに報告する（別の作業として提案する）。

## 3. 検証
- プロジェクトの型検査・lint・単体テストを全部通す（コマンドはプロジェクトのもの）。build は統合先に入れる直前の最終の状態で 1 回（`chk-run.sh`）。
- 失敗したまま先へ進まない。直してから回し直す。

## 4. レビュー → 直す
- 実装した AI とは別のレーンでレビューする（[review-loop](../review-loop/SKILL.md)）。判定は最終行の `VERDICT:` だけ。
- P0 / P1（重大）が残っている間は push も PR もしない。P2 / P3（軽微）の扱いは review-loop の決まり（round 3 以降は後回しの票へ）に従う。
- 「対応不要」と判断するのは、コードが正しい・仕様どおりだと確かめられたときだけ。面倒・軽微を理由にしない。
- **適度なところで締める**: 周回が `LANES_REVIEW_MAX_ROUNDS`（既定 5）を超えて `GATE: ESCALATE` になったら、それ以上直し続けずに人に「続けるか・締めるか」を聞く。仕組み上防げないものは `.lanes/accepted-limitations.md` に書いて受け入れる。公開・リリース前のレビュー周回の途中では、新しい機能を足さない（[運用ルール](../../docs/operating-rules.md)「1.5」）。

## 5. commit
- 件名は `種類: 内容`（`feat:` `fix:` `docs:` `test:` `refactor:` `chore:` など）。プロジェクトに決まりがあればそれに従う。
- 本番に出る枝（`main` など）への取り込み・本番デプロイ・本番 DB の変更・課金の本番切り替えは、**人の GO を待つ**（[運用ルール](../../docs/operating-rules.md)）。

## テストを足す決まり
- **新しい機能**: 機能と同じ commit に、その意図を確かめるテストを最低 1 件。
- **バグ修正**: そのバグの症状を再現するテストを書き、直した後に通ることを示す（直す前のコードでは赤になること）。
- 書く目安（プロジェクトに規約が無いとき）:

  | 対象 | 書くか |
  |---|---|
  | 変換・計算・入力の検査などの純粋な関数 | 必ず |
  | サーバー側の処理の分岐（認可・入力の検査） | なるべく（外の依存は差し替える） |
  | 画面の見た目・操作 | プロジェクトの E2E（画面を通した試験）の方針に従う |
  | スナップショット（出力の丸写し） | 原則書かない（壊れやすい） |

  3 行以上の分岐・計算・変換があれば書く。1 行の包み関数や単純な取り出しは書かない。

## ドキュメントを同じ commit で直す
コードを変えたら、ずれる文書を同じ commit で直す（別にするなら `docs:` の commit をすぐ続ける）。commit の前に確かめる:
- [ ] 使い方・コマンド・オプションを変えた → README・手順書
- [ ] 設定や環境変数を足した・変えた → 設定の説明と見本（`.env.example` など。値は書かない）
- [ ] 機能を足した・消した → 機能の一覧・ロードマップ
- [ ] DB の構造を変えた → スキーマの説明と型の再生成を同じ commit に。本番 DB への反映は人の GO
- [ ] 設計の判断（何を選び、なぜか）をした → 設計の文書や決定の記録
- 内部の整理だけ・誤字・整形だけなら不要。

## 依存の更新
- 脆弱性の対応で `npm audit fix --force` のような強制の更新は使わない（主なライブラリが大きく版上げされて壊れる）。影響の小さい更新だけを当てる。
- 主なライブラリ（フレームワーク・決済・認証・AI の SDK など）の大きな版上げは、それだけで PLAN を出して GO をもらう。上げた後は 3 の検証を全部通す。

## 残った作業
- レビューや調査で見つかった軽い残りは、その場で片付ける。大きいものは別の作業として記録し、人に伝える。「余裕があれば」で流さない。
