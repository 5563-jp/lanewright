# 自律ジョブの見張り（autonomous-run-watchdog）

長いレーンを待っているバックグラウンドのコーディネーター（取りまとめ役のサブエージェント）は、ターンを終えて黙りがちで、そうなると作業が進まなくなる。また、独立して進められる部分があっても全部を 1 本の直列で回しがちである。このスキルは最初に並列計画を強制し、長いジョブには毎回次の 2 つのルーティンを並走させる。
- **5 分の見張り**: 止まりを見つける
- **10 分の見直し**: 並列度を保つ

## `<kit>/lanes/lanes-watch.sh` との役割分担

共通ランチャ（レーンを起動・管理するスクリプト）の `<kit>/lanes/lanes-watch.sh` と重なる部分があるため、次のように使い分ける。

- **`<kit>/lanes/lanes-watch.sh`（機械の見張り。常に使う）**:
  - Mac のレーン（`<kit>/lanes/run-impl.sh` / `<kit>/lanes/run-review.sh` / `<kit>/lanes/run-qa.sh` など、`logs/*.pid` を持つもの）の終了・止まり・open PR（変更を統合するためのレビュー依頼）を 5 分ごとに見て、`$LANES_RUNS_ROOT/.lanes-watch.heartbeat`（heartbeat：生存確認用の定期更新ファイル）を更新する。
  - `LANES_COMMANDER=claude`（Claude デスクトップ等）では `zsh <kit>/lanes/lanes-watch.sh --until-wake` をバックグラウンドで回し、`WAKE:` で起きて次工程をつなぎ、監視を再開する。外側の Bot（`LANES_COMMANDER=grok` 等）は、5 分ルーティンで `<kit>/lanes/lanes-monitor.sh`（1 回分の巡回）を回すか、`lanes-watch.sh` を `<kit>/lanes/detach-run.sh` で 1 本だけ常駐させる（`--until-wake` なしの `lanes-watch.sh` は終わらないので、ルーティンのたびに起動しない）。
  - 10 分ごと（`LANES_CHECK_INTERVAL_MIN`）に `<kit>/lanes/lanes-watch.sh --check` で watch 自体の生存（`WATCH OK` / `WATCH STALE` / `WATCH DEAD`）と、稼働数（`LANES RUNNING`）・次工程待ち（`直近N分 DONE（次工程待ち）`（N は `LANES_CHECK_INTERVAL_MIN`、既定 10））を見る。STALE / DEAD なら watch を再起動する。
  - スクリプトは作業レーンを自動起動しない。次工程をつなぐのは親（司令塔）の役割。
- **このスキル（判断の見張り。コーディネーターに任せるときだけ足す）**:
  - 親がサブエージェントのコーディネーターにジョブを預けたときに、「コーディネーターが黙っていないか」「並列にできる作業を出し忘れていないか」を見る。レーン個々の生死は自前で調べ直さず、`lanes-watch.sh --check` と `<kit>/lanes/lanes-status.sh` の結果を読む。
- **目安**: 親が自分でレーンをつないでいるだけなら `lanes-watch.sh`（＋`--check`）だけで足りる。コーディネーターに預ける長いジョブ・夜通しのジョブでは両方を同時に動かす（5 分の見張りは `lanes-watch.sh` の heartbeat とコーディネーターの heartbeat の両方を見る）。

## 最初のレーンを起動する前に: 並列計画（必須）

新規プロジェクトや「土台作り」1 本だけのゴールも含め、すべてのジョブに適用する。1 本の直列に見えるゴールでもそのまま受け入れない。

1. ゴールをトラック（並行して進める作業の筋）に分け、status ファイルの先頭の `PARALLEL PLAN` 見出しの下に書く。トラックごとに「何をするか」「何に依存するか」「誰が回すか（`<kit>/lanes/run-impl.sh` の Claude / Gemini、`<kit>/lanes/run-review.sh`、クラウドエージェント。モデルは設定ファイルと `<kit>/lanes/lanes.env` で管理）」「今すぐ始められるか」を記載する。
2. 次のチェックリストを確認し、当てはまる項目ごとにトラックを足す。未完のトラックに依存しないものは、本線のレーンと同じ瞬間に始める:
   - 完成したコードを必要としないインフラ・設定（ホスティング設定、ルートディレクトリ、環境変数、ドメイン、DNS（ドメイン名と IP アドレスの対応設定）、CI（自動テスト・ビルド）の骨組み、リポジトリ設定）
   - すでに commit（変更の記録）済みのものの早めの読み取り専用レビュー（最後のレビューを短くするため）
   - 自分の枝・worktree（Git で別フォルダに展開した作業ツリー）で作って後で rebase（変更の基点となるブランチを付け替える操作）できる、追加の機能・コンテンツの票（2 本目のデモ、ページ、文言、テスト）
   - UI（画面表示）がある場合のデザイナー・フロントエンド（画面側）・バックエンド（サーバー側）のデザイン・文言作業
   - 票とドキュメントの手入れ（次の票を作る、親票に進捗を書く）
   - コードが入る前に用意できる検証の準備（Preview（本番公開前の確認用環境）の確認、テストデータ、スクリプト）
3. トラックごとに合う中でいちばん軽いレーンを使い、順番待ちにせずレーンを足す（レーンの同時本数は無制限）。待ってよいのは本当の依存（同じファイル、マージ済みのコードが要る、ユーザーの GO（実行許可）が要る）だけで、待つトラックには何を待っているかを status ファイルに書く。実装の Claude / Gemini の振り分けは [lanes](../lanes/SKILL.md) に従う。
4. コーディネーターには本線だけでなく計画全体を渡し、「起動できるトラックを全部動かし続けることもゴールの一部」と伝える。

## ジョブを始めるとき

1. **ゴールと停止条件**を 1 行で決める。それと `PARALLEL PLAN` 節、依存一覧をジョブの status ファイルの先頭に書く。
2. **コーディネーター用の heartbeat ファイル**を status ファイルの隣に決める（例: `<job-dir>/coordinator-heartbeat.txt`）。`lanes-watch.sh` の heartbeat（`$LANES_RUNS_ROOT/.lanes-watch.heartbeat`）とは別物。
3. **コーディネーターへの指示**（起動プロンプトに入れるか、実行中ならメッセージで送る）:
   - レーンを待つ間にターンを終えない。ゴールに着くか本当のブロッカーに当たるまでループを続け、決めた間隔で定期報告を送る。
   - 各ステップの後に heartbeat ファイルを 1 行で上書きする（現地時刻、いま動いている全トラック、次に何を待っているか）。
   - レーンが終わったら（終了コード、レビューの `CLEAN` / `NEEDS_FIX`）、数分以内に次のステップ（レビュー・修正・PR・マージ）を始め、同時に依存が解けたトラックも始める。
   - レーンは共通ランチャだけで起動する（`<kit>/lanes/detach-run.sh` 経由。手書きの `run-*.sh` や `nohup &` は禁止）。起動後 60 秒以内に `<kit>/lanes/lanes-status.sh <worktree> <label> --tail 20` を見るまで「起動した」と言わない。
4. **ルールを status ファイルに書く**（どのルーティンからも見えるように）: heartbeat のパス、止まりの閾値、「既存のコーディネーターを再開する。2 つ目は絶対に起動しない」。レーンを始める前に status ファイル・ロックファイル（`logs/<label>.lock`）・動いている worktree を確認し、二重に出荷・migration（データベース構造の変更）しないようにする。
5. **5 分の見張りを作る**（5 分ごと）。プロンプトの内容:
   - まず heartbeat ファイルの更新時刻を読む。**heartbeat が新しければ（10 分以内に更新）、最小限の読み取りで終える**: heartbeat の行と 1 回分のレーン状態（`lanes-watch.sh --check`、必要なら `lanes-status.sh <worktree>`）まで。ログ・証跡・PR・status ファイル全体は読み直さず、確認済みの結果を確かめ直さない。heartbeat が古いときだけ中身と status ファイルの最新行を読む。レーンの終了状態はプロセスの引数や秘密を表示しない方法（`lanes-status.sh`・`.done`）でだけ確認する。
   - 次のどれかなら止まりとみなす: (a) heartbeat が 10 分以上更新されていない、(b) レーンが exit 0・`NEEDS_FIX`・`CLEAN` になって 10 分以上たつのに次のステップが始まっていない（`lanes-watch.sh --check` の「直近N分 DONE（次工程待ち）」（N は `LANES_CHECK_INTERVAL_MIN`）も手がかり）、(c) 動いているトラックが 1 本だけなのに、`PARALLEL PLAN` に今すぐ始められる別トラックがある、(d) 同じ確認を 2 回以上回している。
   - 止まりなら親に 1 行 `COORDINATOR_STALLED: <理由>` を返す。それ以外は黙って終わる。ユーザーに直接メッセージしない。本番には絶対に触らない。
6. **10 分の見直しを作る**（10 分ごと、見張りとタイミングをずらす）。プロンプトの内容:
   - 終わった作業・open PR・動いているレーン・`PARALLEL PLAN` を突き合わせる。前回の見直しから変わったもの（新しい DONE / EXIT、新しい PR）だけを読み、確認済みの作業は検証し直さない。
   - 上のチェックリストを現状に当て直す。「全部同じ枝の 1 本道」は受け入れられる結論ではない。別の枝・設定・レビュー・票・デザインで回せる作業を探し、コーディネーターに今すぐ始めさせる。
   - 依存は満たしたのにまだ始まっていない票・トラックがあれば、優先度を理由に待たせず今すぐ並列で始めるようコーディネーターに渡す（「優先度が低いから後で」は止まりと同じ扱いで直す）。
   - 詰まっているものがあればコーディネーターに直させる。2 つ目のコーディネーターは絶対に起動しない。
   - 見張りの照合: 5 分の見張りが直近 15 分（3 回分）に動いていない、またはコーディネーターの heartbeat が 10 分より古い、または `lanes-watch.sh --check` が `WATCH STALE` / `WATCH DEAD` なら、親に `WATCHDOG_STALE: <理由>` を返す（watch の再起動は親が行う）。
   - 本番に触るものはユーザーの GO を待つ。作業を足した・止まりを直した・ユーザーの判断が要る、のどれかのときだけ親に短いメモを返し、それ以外は黙って終わる。ゴールに着いたら両方のルーティンを消すよう親に伝える。
7. コーディネーターの ID、両ルーティンの ID、heartbeat のパス、ゴールを status ファイルに記録する。

## ルーティン起床時・ユーザー確認時・ゴール到達時

- **ルーティンに起こされたとき**: 同じコーディネーターを再開し、何が詰まっていたか・何を足すかを伝える。新しいコーディネーターは起動しない。ユーザーに伝えるのは、作業を足したとき・計画が変わる形で止まりを直したとき・ユーザーの判断が要るときだけ。
- **ユーザーに「全部並列で回ってる？」と聞かれたとき**: 失敗のシグナルとして扱う（計画の並列度が足りなかった）。同じターンで計画を直して足りないトラックを起動する。
- **ゴールに着いたとき**: 両方のルーティンを消し、heartbeat ファイルに最後の行を書いて結果を報告する。`lanes-watch.sh` は動いているレーンが無くなれば止めてよい。

## 同じ確認を繰り返さない・教訓

- **見張り（5 分）・見直し（10 分）**: heartbeat が新しければ最小限の読み取りで終え、前回からの変化だけを見る。
- **コーディネーターへの指示にも入れる**:
  - レビューは `<kit>/lanes/run-review.sh` で呼び、round は label 末尾 `-r<N>` で必ず渡す。使える機能は Codex レビュー・Claude レビューのどちらの構成でも同じ（`zsh <kit>/lanes/lanes-roles.sh --print` でどちらが走るかを確かめる）:
    - **どの構成でも**: `--mode auto`（既定）で、初回は `full`（全体差分レビュー）、前回 `CLEAN` の後は前回 HEAD（ブランチ先端のコミット）からの `delta`（増分レビュー）、同一 HEAD は `skip-same-head`（レビューせず前回判定を返す）、前回 `NEEDS_FIX` の後は自動で `full` に戻して未解決指摘を引き継ぐ。round 3 以降は P0/P1（重大・高優先度の指摘）だけが止め、P2/P3（中・軽微な指摘）は `logs/<series>.followups.md` に出て `CLEAN` で通る。`--round N` も使える。
    - **必須検証の使い回し**: 最終 HEAD で `<kit>/lanes/chk-run.sh` を通してからレビューを呼ぶと、同じ中身ならレビュアーは typecheck / lint / unit を回さない（ランチャが `chk-run.sh --query` で判断する。`chk-run.sh` とレビューは同じシェルから呼ぶ）。
  - build（配布・実行用ファイルの生成）はレビュー・修正レーン・bot QA（品質確認）では回さない（レビューで省略してよいのは build だけ）。E2E（画面を通した通しのテスト）は、レビュー用テンプレート `<kit>/lanes/templates/claude-review-{full,delta}.md` のとおり full ではプロジェクトにあれば完走、delta では差分が画面・API に触れたときだけ該当の spec を回す。統合先ブランチ（`LANES_BASE_BRANCH`）に入れる直前の最終 HEAD で `<kit>/lanes/chk-run.sh` を 1 回（同一 git tree（ファイル構成と中身の識別子）・同一 `input_fp`（環境や依存の指紋データ）なら自動省略）と CI で担保する。
  - 同じ確認を 2 回以上回している場合（同一 git tree の chk 再実行、`--force` で同じ HEAD を 2 回以上レビューしている場合など）は止まりとみなし、`COORDINATOR_STALLED: 同じ確認の繰り返し <内容>` を返す。同一 HEAD を呼び直して `skip-same-head` が返るのは、ランチャが省略した正常な動作なので止まりではない（どの構成でも。`--force` で何度もやり直しているときだけ止まり）。
- **運用上の注意**:
  - レーンが使用中のランチャスクリプトをその場で直接書き換えない（別ファイルに書いて `mv` で差し替える）。
  - Gemini レーンの `--verify` 等を足す前に、対象パッケージにそのコマンドが存在するか確認する。新しい worktree ごとにレーン起動前の依存導入を確認する。
