# レビューの出し方（必須）
- 1 回のレビューで見つけた問題は、重さ順（P0 → P1 → P2 → P3）に **全部** 列挙する。上位の数件で止めない。
- 同じ種類の問題は、該当する箇所を差分全体からすべて挙げる（1 か所だけ挙げて「ほかも同様」で済ませない。箇所ごとに指摘を分ける。ただし同じ原因で 1 つの直し方で済むものは、下の「作りの問題」のとおり 1 件の本文に全箇所を書く）。
- 重さの目安：P0＝データ消失・情報漏えい・本番停止／P1＝利用者に誤った結果・認可・課金・個人情報の取り違え／P2＝条件付きで起きる不具合・テストの不安定さ／P3＝説明・書式・軽微。

## 重さの決め方（必須）
- P0 / P1 には、指摘ごとに「起きる条件」（普通の使い方・普通の入力で起きるか。起きるなら手順）と「影響」を 1 行ずつ書く。
- P0 / P1 にするのは、普通の使い方・普通の入力で起きて、上の目安の影響が出るもの（要件の退行を含む）。
- 秘密の値・認証と認可・お金（課金・決済・価格）・本番のデータ・個人情報に関わるものは、起きにくい条件でも重さを下げない。
- それ以外で起きにくい場面（処理の途中での強制終了や停止の合図、容量不足などの書き込み失敗、同じ作業場所での同時実行、操作する人が自分で持ち込む環境変数やファイル、実際のデータ元が返さない形の入力）は P2 にして、起きる条件と影響を書く。結果が安全な側に倒れるだけ（止まる・人の確認に回る・やり直せば直る）なら P3。受け入れ済みの限界（指示書にあれば）に当たるものはそちらが優先で、この分類はその外にだけ使う（似た条件でも、受け入れていない影響は別に重さを付ける）。
- 前回の直しで足したコードに出た問題は、そう書く。同じ原因で同じ直し方になる穴は、全箇所を本文に書いて 1 件にまとめ（「作りの問題」）、単純にする直し方（範囲を絞る・既存の仕組みに乗せる・迷ったら安全な側に倒す 1 か所の判定にする）を書く。別々の直しが要るものは分ける。

## 秘密の値の扱い
- `ps`・`/proc` などでプロセスの引数（コマンドライン）や環境変数を表示しない。ほかのツールの鍵が引数に乗っていることがある。
- `.env`・`.env.*`・`env`／`printenv` の出力・鍵ファイル・トークンを読まない・出力しない。秘密らしい値を見つけたら、値を書かずに「どのファイルの何行目」だけ報告する。
- **`.env.example`・`.env.sample` などの見本のファイルも含めて、`.env*` を grep・cat・rg・head・sed で開かない。行を絞った grep もしない。** 必要な変数の名前は、ソースの `process.env.XXX` や README から拾う。
