# 運用ルール

キットのランチャは多くの事故を機械で止めますが、止められないもの（判断・報告・順番）は運用で守ります。
ここに書いたルールは、自分の `AGENTS.md` / `CLAUDE.md` に貼れる形で `templates/AGENTS.md.example` と `templates/CLAUDE.md.example` にも入れてあります。

用語:
- **レーン**: 1 作業 = 1 worktree = 1 ランチャ。`label`（英数と `. _ -`）で呼び分ける。
- **司令塔**: レーンを起動し、終わったら次工程へつなぐ役（人、外の Bot、Claude の Code タブのどれか）。
- **重大度**: P0（致命的）/ P1（重大）/ P2（中程度）/ P3（軽微）。S-*（仕様の確認。コードの欠陥ではない）。

## 1. レビューは必須、重大度ごとに再レビュー

- 実装したら**必ず別のレーンでレビューする**。レビューを通していない変更を PR にしない。
- レビューは読み取り専用で回す（`run-review.sh`）。判定は最終行の `VERDICT: CLEAN` / `VERDICT: NEEDS_FIX` だけ。`VERDICT: NONE`（途中で切れた・判定なし）は失敗として回し直す。
- **P0 / P1**: 直したら必ず full（全体）で再レビュー。ゼロになるまで「直す → 再レビュー」を繰り返す。残っている間は push も PR もしない。
- **P2 / P3**: 必須のループではないが、ロジック・エラー経路・テストを触った直しなら原則もう一度レビューする。軽い直しは delta（前回 CLEAN からの差分だけ）でよい。
- **S-***: コードの欠陥ではないので、仕様を決める人に確認する。

## 2. レーン内の自己レビューは最大 2 回

- 実装レーンは自分の差分を見直してよいが、**最大 2 回まで**。2 回目の後に残るのが P3 だけなら、直せるものは直して終わる。3 回目には入らない。
- 品質の最終担保は後ろのレビューレーン。レーンの中で完璧を目指して止まらない。
- ただし指示書にある検証（型チェック・lint・単体テストなど）は省略しない。
- 自己レビューの前に、そこまでの作業を commit しておく。

## 1.5. 適度なところで締める

周回が終わらなくなるのを防ぐため、締め方を 3 つの仕組みで決めている。
- **周回の上限**: `LANES_REVIEW_MAX_ROUNDS`（既定 5）。上限を超えた周で `CLEAN` にならなければ、P0/P1 が残っていてもランチャが `GATE: ESCALATE` で止まる。司令塔はそこで修正を続けず、指摘の一覧を付けて人に「直して続けるか・締めるか」を聞く。続けるなら人が上限を上げる。周回は系列（label の末尾 `-r<N>` を外した名前）ごとに数えるので、label の頭を変えずに `-r<N>` だけ増やす。
- **受け入れ済みの限界**: 人が「直さずに受け入れる」と決めた種類（仕組み上防げないもの・想定する脅威の外のもの）は、対象リポの `.lanes/accepted-limitations.md` に書く。レビューの指示書に必ず入り、当てはまる指摘は P0〜P2 にしない。締めるときは、残りをここか後回し票（`logs/<系列>.followups.md` や Issue）へ移す。
- **締め切り前は機能を足さない**: 公開・リリース前のレビュー周回の途中では、新しい機能を足さない（足すたびに新しい指摘が出て周回が延びる）。足すなら人の GO を取り、その機能は別の系列（新しい label）として 1 周目から数える。

## 3. ビルドは最後に 1 回だけ

- 同じ確認を何度も回さない。**ビルドは、取り込み直前の最終の head（最新の commit）で `chk-run.sh` と CI に 1 回だけ担保させる。**
- 実装・レビュー・修正のレーンでは、型チェック・lint・関連テストまでにして、ビルドは回さない。
- 順番は「実装 → `chk-run.sh`（確認を記録）→ レビュー」。レビューは同じ中身の記録があれば型チェック・lint・単体テストを回し直さない（`LANES_REVIEW_REUSE_CHECKS`）。レビューで直したら、また `chk-run.sh` から。
- `chk-run.sh` は、同じ中身をすでに全部通していれば何も回さない（`--force` で必ず回す）。

## 4. 全レーンで MCP を使わない

- レーンの CLI には MCP（外部サービスへ AI が直接つながる仕組み）を読み込ませない。本番の決済・DB などへ AI が直接届く経路を断つため。
  ランチャが Claude・Codex・Gemini それぞれのやり方で遮断する。
- 外部サービスの調査が必要なら、司令塔（人か司令塔のセッション）が先にやって、結果を指示書に書く。
- **MCP は止めても、各 CLI の指示ファイルは読み込まれる**。`~/.claude/CLAUDE.md`・`~/.codex/AGENTS.md`・`~/.gemini/` の下の指示（`GEMINI.md` など）、
  対象リポジトリの `CLAUDE.md` / `AGENTS.md`、Claude の `~/.claude/settings.json` のフック（決まった時に自動で動く処理）は、レーンの AI にも効く。
  - commit の作者・署名・言語・口調などの指示は、レーンでもそのまま守られる。commit の作者は対象リポジトリの `git config user.name` / `user.email` で決めるほうが確実。
  - 「計画を出して承認を待つ」のような**人の返事を待つ指示**は、非対話のレーンでは止まる原因になる（`STALLED` になる・何もせずに終わる）。
    指示ファイルに「レーン（非対話）では承認を待たずに進める」と書くか、指示書の先頭に書く。
  - 指示ファイルに鍵や個人の情報を書いていれば、それもレーンの AI に渡る。

## 5. 同じ label は 1 本だけ

- 同じ label のランチャが動いている間、または前回の子プロセスが生きている間は、起動を拒否する（exit 2）。
- 止めるのは `kill <ランチャの pid>`。ランチャは子の終了を待ってから `.done` を書く。`kill -9` はしない。
- `FAILED` / `DEAD` の行に「子 pid=N 生存」と出たときだけ、その子を `kill N` してから起動し直す。`RUNNING` / `STALLED` の子は健全なので止めない。

## 6. 起動したと言う前に生死を見る

- 起動したら **60 秒以内に** `lanes-status.sh <worktree> <label> --tail 20`。`RUNNING` か `DONE` 以外は起動失敗として末尾付きで報告する。
- **status を見る前に「起動した」と言わない。** 言うなら「起動確認 OK: pid / ログのパス」。
- 以後は 5 分ごとの見回り（`lanes-watch.sh`）と定期の生存確認（`lanes-watch.sh --check`。既定 10 分ごと、`LANES_CHECK_INTERVAL_MIN`）で追う。
- 報告は毎回同じ 4 点: **状態 / 経過時間 / 最終出力の時刻 / 次にやること**。`FAILED` / `DEAD` / `STALLED` は聞かれる前に報告する。
- `DONE` は待たずに次工程へ。スクリプトで全工程を自動連鎖させる仕組みは作らない（つなぐ判断は司令塔）。
- 長く動くランチャは親を残して起動する。短い Shell の中で `nohup ... &` だけして親を終わらせない。

## 7. CI 待ちのレーンを作らない

- PR を作ったら `gh pr merge <PR> --auto --merge --delete-branch` で GitHub の auto-merge に任せる。Mac で CI を待たない。
- 次の見回りのついでに `gh pr view <PR> --json state,mergedAt` を見て、マージ済みなら `cleanup-after-merge.sh <worktree> --apply`。
- 必須チェック（ブランチ保護）が無いリポジトリでは `--auto` が CI を待たずに即マージになる。その場合だけ `gh pr checks <PR> --watch --fail-fast` を 1 回待ち、緑なら手でマージ、赤なら止めて報告する。
- CI の設定（`.github/`）を触った PR だけは、初回の実行を `gh run watch <run-id> --exit-status` で 1 回確かめる。

## 8. 本番は人の GO

- `main`（本番に出る枝）への取り込み・本番デプロイ・本番 DB の変更・課金の本番切り替え・アプリストアへの提出は、**人の明示の GO** を待つ。
- 本番向けの取り込み（リリースの PR）は auto-merge しない。
- まだ公開しない機能は、フラグで隠したまま取り込み先（例 `develop`）とプレビュー環境まで進めてよい。

## 9. 残タスクは軽微でも片付けるか、別タスクにする

- レビュー・調査・実装で見つかった残りの作業は、**軽微でも放置しない**。「任意」「余裕があれば」で流さない。
- 数分で終わるもの（注記・ログ・コメント・テスト 1 件など）は、その場で片付ける。
- 大きいものは別のタスクとして、Issue や残タスク表に確実に記録する（記録は消さない）。
- 「対応不要」と判断してよいのは、コードが正しい・仕様どおりだと確かめられたときだけ。
- 作業の区切りで、残タスクが全部「完了」か「別タスクとして記録済み」かを確かめる。

## 10. 秘密を表示しない

- API キー・パスワード・トークンなどの値を、チャット・ログ・PR・Issue に出さない。**末尾の数文字も出さない。** 伝えてよいのは「どのファイルの何行目にある」「文字数」「形式（`sk-...` など）」まで。
- `.env` 系のファイル（見本の `.env.example` も含む）を AI に開かせない。必要な変数名はソースや README から拾う。
- プロセスの引数や環境変数の一覧（`ps` の引数表示・`env`・`printenv`）を表示しない。ほかの道具の鍵が載っていることがある。
- 一度でも表示されてしまった秘密は、漏れたものとして扱い、すぐに無効化して作り直す。
- CLI はサブスクのログインで使い、API キーでは起動しない（ランチャが API キーの環境変数を外し、ログイン方法を確かめる）。

## 11. 一時ファイルと作業範囲

- レーンの一時ファイル（一時 DB・ビルド出力・ログ・diff など）は、ランチャが渡す `$LANES_SCRATCH`（= `$TMPDIR`）の下にだけ置く。`~/Downloads`・ホーム直下・デスクトップ・`/tmp` には置かない。
- レーンは指示書で決めた範囲のファイルだけ触る。範囲外の直しが要ると気づいたら、触らずに最終報告に「どのファイルの何を」と書く。
- レーンの中では `git push` の強制（force push）・枝の切り替え・stash・reset をしない。
- 対象リポジトリの `.gitignore`（または `.git/info/exclude`）に `logs/` を入れておく。ランチャが worktree の `logs/` に記録（指示書の全文・ログ・証跡）を書くので、
  無視していないと未追跡のまま残り、AI が誤って commit することがある。`lanes-doctor.sh <worktree>` で無視されているかを点検できる。
